# TS43 Route Documentation

This document describes the TS43 Express router implemented in `routes/ts43.js`. It focuses on the flow, endpoints, and key helpers used to orchestrate a CIBA plus DCQL-based SIM verification.

## Location and Mounting

- **File**: `routes/ts43.js`
- **Mounted at**: `/ts43` (see `app.js`)

## Responsibilities

- Validate client configuration using `findClientByClientId`.
- Start a CIBA authentication request and retrieve an `auth_req_id`.
- Request a DCQL payload for a digital credential request.
- Accept a `vp_token`, exchange for an access token, and fetch user info.
- Store session data to drive the UI display.

## Endpoints

### POST `/ts43/auth`

Starts the TS43 flow by:

1. Posting to the CIBA auth endpoint to obtain `auth_req_id`.
2. Calling the DCQL endpoint using `auth_req_id` as a bearer token.
3. Returning the auth request ID, a generated nonce, and a digital request payload.

**Request body**:

- `client_id` (string, required)
- `login_hint` (string, optional)
- `carrier_hint` (string, optional)
- `operation` (string, optional)
- `scope` (string, optional)

**Response**:

- `auth_req_id` (string)
- `nonce` (string)
- `digital_request` (object)

#### Response JSON Structure

The server responds with:

```json
{
  "auth_req_id": "<auth_req_id>",
  "nonce": "<uuid>",
  "digital_request": {
    "protocol": "openid4vp-v1-unsigned",
    "data": {
      "response_type": "vp_token",
      "response_mode": "dc_api",
      "nonce": "<uuid>",
      "dcql_query": {
        "credentials": [{}]
      }
    }
  }
}
```

**Notes**:

- `digital_request.data.dcql_query.credentials[0]` is the payload returned by the TS43 DCQL endpoint.
- `nonce` at top-level and inside `digital_request.data` uses the same value.

#### CIBA Auth Call Details

The server calls the CIBA auth endpoint:

- **URL**: `${auth_server_url}/realms/${realm}/protocol/openid-connect/ext/ciba/auth`
- **Method**: `POST`
- **Content-Type**: `application/x-www-form-urlencoded`

**Form body** (sent by server):

- `client_id`
- `client_secret`
- `scope` (from request or client default)
- `login_hint` (optional)
- `carrier_hint` (optional)

**Minimal example**:

```bash
curl -X POST "$AUTH_SERVER_URL/realms/$REALM/protocol/openid-connect/ext/ciba/auth" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "client_secret=$CLIENT_SECRET" \
  --data-urlencode "scope=openid" \
  --data-urlencode "login_hint=+1234567890" \
  --data-urlencode "carrier_hint=carrierX"
```

#### TS43 DCQL Call Details

After receiving `auth_req_id`, the server calls the DCQL endpoint:

- **URL**: `${auth_server_url}/realms/${realm}/protocol/openid-connect/ext/bc/ts43/dcql`
- **Method**: `POST`
- **Content-Type**: `application/json`
- **Authorization**: `Bearer ${auth_req_id}`

**JSON body**:

```json
{
  "operation": "GetPhoneNumber",
  "nonce": "<uuid>"
}
```

**Minimal example**:

```bash
curl -X POST "$AUTH_SERVER_URL/realms/$REALM/protocol/openid-connect/ext/bc/ts43/dcql" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $AUTH_REQ_ID" \
  -d '{"operation":"GetPhoneNumber","nonce":"<uuid>"}'
```

### POST `/ts43/token`

Completes the TS43 flow by:

1. Posting `vp_token` to the callback endpoint.
2. Exchanging `auth_req_id` for an access token at the token endpoint.
3. Fetching user info and storing it in the session.

**Request body**:

- `vp_token` (string, required)
- `auth_req_id` (string, required)
- `client_id` (string, required)
- `nonce` (string, required)

**Response**:

- On success: user info JSON
- On error: error JSON (also stored in session for UI visibility)

#### Token Flow Details (External Calls)

This endpoint coordinates three server-to-server calls. The client only calls `/ts43/token`, but the service will:

1. **Send VP token to TS43 callback**
2. **Exchange `auth_req_id` for an access token**
3. **Fetch user info using the access token**

These steps are required for the SIM-based flow to complete.

#### 1) TS43 Callback (VP Token Submission)

- **URL**: `${auth_server_url}/realms/${realm}/protocol/openid-connect/ext/bc/ts43/callback`
- **Method**: `POST`
- **Content-Type**: `application/json`
- **Authorization**: `Bearer ${auth_req_id}`

**JSON body**:

```json
{
  "vp_token": "<vp_token>"
}
```

**Expected response (typical)**:

```json
{
  "status": "ok"
}
```

Some deployments may return an empty body or a vendor-specific payload. The service only requires a 2xx response to proceed.

**Minimal example**:

```bash
curl -X POST "$AUTH_SERVER_URL/realms/$REALM/protocol/openid-connect/ext/bc/ts43/callback" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $AUTH_REQ_ID" \
  -d '{"vp_token":"<vp_token>"}'
```

#### 2) Token Exchange (CIBA Token Endpoint)

- **URL**: `${auth_server_url}/realms/${realm}/protocol/openid-connect/token`
- **Method**: `POST`
- **Content-Type**: `application/x-www-form-urlencoded`

**Form body**:

- `client_id`
- `client_secret`
- `grant_type` = `urn:openid:params:grant-type:ciba`
- `auth_req_id`

**Minimal example**:

```bash
curl -X POST "$AUTH_SERVER_URL/realms/$REALM/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode "client_secret=$CLIENT_SECRET" \
  --data-urlencode "grant_type=urn:openid:params:grant-type:ciba" \
  --data-urlencode "auth_req_id=$AUTH_REQ_ID"
```

**Success response (typical)**:

```json
{
  "access_token": "<access_token>",
  "expires_in": 300,
  "refresh_expires_in": 0,
  "token_type": "Bearer",
  "scope": "openid"
}
```

**Error response (typical)**:

```json
{
  "error": "authorization_pending",
  "error_description": "The authorization request is still pending."
}
```

#### 3) User Info Request

- **URL**: `${auth_server_url}/realms/${realm}/protocol/openid-connect/userinfo`
- **Method**: `GET`
- **Authorization**: `Bearer ${access_token}`

**Minimal example**:

```bash
curl -X GET "$AUTH_SERVER_URL/realms/$REALM/protocol/openid-connect/userinfo" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
```

**Success response (typical)**:

```json
{
  "sub": "<subject>",
  "phone_number": "+1234567890",
  "phone_number_verified": true
}
```

#### Client-Facing Response From `/ts43/token`

On success, the endpoint returns the **user info JSON** from the userinfo call.

On error, it returns:

```json
{
  "error": "<message>",
  "status": 500,
  "data": {}
}
```

`data` is included when the upstream service returns a body.
